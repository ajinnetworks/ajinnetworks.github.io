SCADA와 HMI는 화면을 예쁘게 만드는 소프트웨어가 아니라 **설비 제어의 책임 경계와 데이터를 정의하는 상위 제어 계층**입니다. 구축 실패의 원인은 대개 화면 디자인보다 PLC 로직, 태그 체계, 알람 우선순위, 통신 장애 시 동작 원칙이 먼저 정의되지 않았기 때문입니다.

## 1. PLC와 SCADA의 책임을 먼저 분리해야 한다

설비의 안전 인터록, 모터 기동 조건, 로봇 충돌 방지, 공정 시퀀스처럼 즉시성이 필요한 기능은 PLC 또는 전용 Safety Controller에 남겨야 합니다. SCADA는 상태 감시, 생산 데이터 수집, 알람 관리, 레시피·권한 관리, 이력 조회를 담당하는 것이 기본입니다.

상위 서버 통신이 끊겼을 때도 설비가 안전한 상태로 정지하거나 제한 운전할 수 있어야 합니다. 따라서 설계 초기부터 **Local Control / Supervisory Control / Safety Control**의 경계를 문서로 고정하는 것이 중요합니다.

## 2. 태그·알람·Historian이 유지보수성을 결정한다

태그는 설비명-유닛-신호종류-상태를 일관된 규칙으로 구성해야 증설 시 혼선을 줄일 수 있습니다. 예를 들어 동일 의미의 운전 신호를 설비마다 다른 이름으로 쓰면 이후 MES, OEE, Historian 연동 비용이 급격히 증가합니다.

알람도 단순 발생 개수보다 **원인·영향·조치 순서**가 중요합니다. Emergency, Trip, Warning, Information 등 우선순위를 정의하고, 동일 원인에서 파생되는 후속 알람은 억제 로직을 적용해야 작업자가 실제 원인을 빠르게 찾을 수 있습니다.

Historian에는 모든 태그를 무조건 저장하지 말고 품질, 설비상태, 생산수량, 에너지, 고장이력처럼 분석 가치가 있는 항목을 샘플링 주기와 함께 선정해야 합니다.

## 3. 통신 구조는 정상 상태보다 장애 상태를 기준으로 설계한다

PLC와 상위 시스템 사이에는 OPC UA, 제조사 전용 Ethernet, 산업용 Ethernet, MQTT 등 여러 방식이 사용될 수 있습니다. 중요한 것은 프로토콜 이름보다 **통신 단절 시 재접속, 데이터 버퍼링, 시간 동기화, 중복 명령 차단**입니다.

서버 이중화를 적용할 경우 Active/Standby 전환 조건과 복귀 절차를 FAT에서 검증해야 하며, 스위치·서버·전원만 이중화하고 실제 네트워크 경로가 하나라면 실질적인 이중화가 되지 않습니다.

## 4. HMI 화면은 운전자의 판단 시간을 줄이는 방향으로 설계한다

메인 화면에서는 설비 전체 상태와 병목 위치가 보이고, 상세 화면에서는 인터록 조건과 수동 조작 권한을 확인할 수 있어야 합니다. 색상은 정상 상태보다 이상 상태를 강조하고, 애니메이션은 꼭 필요한 경우에만 사용하는 편이 좋습니다.

특히 수동운전 화면에는 출력 명령만 배치하지 말고 현재 조건, 금지 사유, 관련 센서 상태를 함께 표시해야 현장 디버깅 시간이 줄어듭니다.

## 5. FAT/SAT에서 반드시 검증할 항목

현장 적용 전에는 정상 운전뿐 아니라 PLC 전원 재기동, 서버 재기동, 네트워크 단절, 센서 고착, 통신 타임아웃, Recipe 오류, 사용자 권한 오류를 시험해야 합니다. 생산 데이터 누락과 시간 동기화 문제도 실제 운영 시 큰 이슈가 되므로 서버·PLC·카메라·로봇의 시각 기준을 통일해야 합니다.

아진네트웍스는 SCADA/HMI를 단독 화면 프로젝트로 보지 않고 PLC·로봇·비전·설비 인터록을 포함한 통합 제어 구조로 검토합니다. 실제 견적과 구축 범위는 PLC 기종, 태그 수, 화면 수, Historian 보존기간, 이중화 범위, MES 연동 요구사항을 확인한 뒤 산정해야 합니다.
