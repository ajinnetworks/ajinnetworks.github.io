노후 PLC 교체는 단순히 CPU와 I/O 모듈을 신형으로 바꾸는 작업이 아닙니다. 실제 위험은 문서와 현장이 다르고, 과거 개조 이력이 래더와 배선에 누적되어 있으며, 로봇·인버터·온도조절기·비전·상위 시스템까지 통신 의존성이 얽혀 있다는 점입니다.

## 1. 첫 단계는 프로그램 변환이 아니라 현장 자산 조사다

마이그레이션 전에 PLC CPU, I/O Rack, Remote I/O, 특수모듈, 네트워크, HMI, 인버터, 서보, 안전회로를 모두 목록화해야 합니다. 도면의 I/O 주소와 실제 결선 상태도 대조해야 하며, Spare I/O와 사용하지 않는 신호를 구분해야 합니다.

프로그램은 최신 백업본인지 확인하고, 온라인 PLC의 실제 프로그램과 비교해야 합니다. 주석이 없거나 비밀번호·소스가 없는 경우에는 단순 자동 변환이 아니라 기능 단위 역분석이 필요할 수 있습니다.

## 2. I/O 1:1 매핑과 기능별 로직 검증이 핵심이다

기존 주소를 신형 PLC 주소에 대응시키는 I/O Mapping Table을 작성하고 Digital, Analog, High-speed Counter, Positioning, Safety 신호를 분리해 관리해야 합니다. 단순 주소 변환만으로는 충분하지 않습니다.

기존 로직을 기동·정지, Auto/Manual, 인터록, Alarm, Recipe, 통신, 복구 로직으로 나눠 기능별로 검증하면 누락 가능성을 줄일 수 있습니다. IEC 61131-3 기반 표준화는 유지보수에 도움이 되지만, 실제 전환 과정에서는 기존 설비의 운전 철학을 먼저 보존해야 합니다.

## 3. 통신 변환은 별도 Work Package로 관리해야 한다

구형 PLC 교체에서 장애가 자주 발생하는 지점은 상위·하위 통신입니다. 로봇 Handshake, 인버터 상태 Word, 비전 결과, HMI 태그, MES 생산지시처럼 데이터 의미가 정해진 인터페이스는 별도 Signal Matrix로 관리해야 합니다.

새 프로토콜을 도입하더라도 명령 ACK, Timeout, Retry, Duplicate Command 차단, 통신 복귀 후 상태 동기화 조건을 정의하지 않으면 양산 중 간헐적 오류가 발생할 수 있습니다.

## 4. Cutover 전에 Shadow Test와 Rollback Plan을 준비한다

가능하다면 신형 PLC 로직을 시뮬레이션하거나 별도 Test Rack에서 I/O와 통신을 검증합니다. 현장에서는 실제 출력은 기존 PLC가 담당하고 신형 시스템은 입력과 상태를 비교하는 Shadow Test 방식도 검토할 수 있습니다.

Cutover 계획에는 정지 시점, 전원 차단, 결선 변경, 프로그램 다운로드, I/O Check, Dry Run, Auto Run, 생산 승인 순서를 포함해야 합니다. 동시에 문제가 발생했을 때 기존 PLC로 돌아갈 수 있는 Rollback 조건과 예상 복구 절차를 미리 정의해야 합니다.

## 5. 견적 산정 시 빠지기 쉬운 항목

PLC 하드웨어 비용만 계산하면 실제 프로젝트 원가가 왜곡됩니다. 현장조사, 프로그램 분석, 전기도면 수정, Panel 개조, I/O 변환, HMI 수정, 통신 시험, 로봇·비전 연동, 시운전, 야간/휴일 Cutover, 생산 입회까지 포함해 산정해야 합니다.

아진네트웍스는 레거시 PLC 마이그레이션을 **현장조사 → I/O/통신 분석 → 로직 재구성 → 사전검증 → Cutover → SAT** 순으로 검토합니다. 실제 생산중단 시간과 투자비는 현장 도면, PLC 백업, 통신 구성, 정지 가능 시간 확인 후에만 확정할 수 있습니다.
